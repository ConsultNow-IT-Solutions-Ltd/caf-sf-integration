1. Executive summary

CAF Compliance keeps critical business applications provably compliant against a catalogue of controls (high availability, backup and restore, disaster recovery, RTO/RPO and similar). Controls generate recurring requests per business application; requests break down into tasks; owners gather evidence; approvers attest; anything overdue drops out of compliance automatically.

The compliance engine — data model, state machine, recurrence, scheduled jobs, approvals and security — runs in ServiceNow. The people who do the work (application owners and approvers) already live in Salesforce. This solution surfaces the full compliance experience in Salesforce without moving any state out of ServiceNow.

Governing rule: ServiceNow is the system of record. Salesforce holds a mirror, never a second opinion.

The two platforms are joined by a bi-directional integration:

  • Outbound (ServiceNow → Salesforce): state. Async business rules push requests, tasks and the control catalogue into Salesforce, upserting by the ServiceNow sys_id.
  • Inbound (Salesforce → ServiceNow): intentions. Salesforce calls a six-resource Scripted REST API to start tasks, upload evidence, attest, read a snapshot and request a re-sync. ServiceNow applies its own rules, then pushes the resulting state back.
  • Assurance. A Sync Health panel detects drift between the two systems and offers per-record repair; every Salesforce callout is logged durably.

Business drivers

DriverOutcome
LicensingApp owners and approvers work in Salesforce, avoiding a ServiceNow fulfiller licence per person.

Low delivery riskZero change to the 24 business rules, 2 flows, recurrence logic and security model in ServiceNow.

2. Scope and objectives

In scope

  • Mirroring CAF Requests, CAF Tasks and the CAF Control catalogue into Salesforce
  • Salesforce compliance grid, drill-in, Approvals, Reports and Admin screens
  • Evidence upload to both platforms; attestation from Salesforce
  • Inbound Scripted REST API with write allow-list and evidence gate
  • Drift detection and manual repair (Sync Health)
  • Durable callout logging and externalised configuration

Out of scope (this release)

  • Moving any state machine or scheduler logic into Salesforce
  • Mirroring relationships, task templates or CMDB records
  • Experience Cloud site for external users
  • Named approver records (sysapproval_approver)
  • Queued/asynchronous inbound calls and automatic retry
  • Row-level security across the integration seam

Objectives

  1. Give application owners a single Salesforce screen that answers "is my application compliant, and what do I do next?".
  2. Guarantee that every state change is decided by ServiceNow rules, regardless of where the user clicked.
  3. Make any disagreement between the two platforms visible within one check, and repairable by one click.
  4. Keep the integration replay-safe, so failures can be repaired by re-pushing without creating duplicates.

4. Architecture principles

#PrincipleImplication
P1Single system of recordAll state transitions, recurrence and approvals execute in ServiceNow. Salesforce never edits a value ServiceNow owns.
P2Mirror, don't replicate configurationOnly requests, tasks and the control catalogue are mirrored. Relationships and templates remain in one place.
P3Intentions in, state outSalesforce asks ("start this task"); ServiceNow decides and pushes the result back.

6.2 Inbound: Salesforce → ServiceNow

One Scripted REST API, six resources, all authenticated. The generic update accepts only an allow-list of six fields:

state · met_criteria · approval · comments · vqd_link · vqd_link_2

Any field outside the allow-list fails the whole call with HTTP 400 and nothing is applied. A partial write the caller cannot see is worse than an error.
CodeMeaning
200Update or attestation applied
201Evidence stored as a sys_attachment
400Empty body, non-allow-listed field, invalid outcome or criteria
404No CAF Task with that sys_id
409Task not In Progress, no longer active, or outcome already recorded
428Evidence gate: no attachment on the task

6.3 Echo-loop guard and explicit reconcile

The echo guard stops a Salesforce-originated change bouncing straight back. On its own it also strands derived changes: cascading rules (for example a task moving its parent request to In Progress) run in the same transaction as the same user, so their pushes are skipped too.

The fix: every inbound resource ends with an explicit reconcile — exactly two upserts, the task and its parent request — triggered by the API request rather than a record change, so no loop can form. A healthy round trip logs one [SF->CAF] line followed by two [CAF->SF] lines.

Do not simplify the reconcile away. Its failure is silent: the mirror simply stops matching, and only Sync Health notices.

8.2 Correlation and lifecycle rules

  • One-directional correlation. No Salesforce Id is stored in ServiceNow. A rebuilt Salesforce org repopulates by re-pushing.
  • Deletes do not propagate, except a deleted control is mirrored as Active__c = false so its grid column disappears.
  • Evidence is held twice, deliberately. Salesforce Files serve preview and download; the ServiceNow attachment is the auditor's copy and the only one the attestation gate counts.
  • Salesforce-only objects: CAF_Integration_Log__c, CAF_Callout_Event__e, CAF_Setting__mdt.

11. Non-functional design

QualityDesign response
ReliabilityOutbound pushes async after commit; inbound calls synchronous with clear status codes; idempotent upserts allow safe replay.
ConsistencyExplicit reconcile after every inbound write; Sync Health compares 3 record types field by field (blank treated as null) and flags checks older than 15 minutes.
ObservabilityEvery Salesforce callout logged to CAF_Integration_Log__c (operation, status, latency, error, user). ServiceNow logs [SF->CAF] / [CAF->SF] lines. Admin screen shows success rate and latency.
Performance limitsEvidence ≤ 2 MB per file (6 MB Apex heap); callout timeout 120 s; one file per Apex transaction.
CapacitySalesforce Developer Edition: 15,000 inbound API requests per day; one end-to-end journey costs roughly 45. Current data: 463 requests, 496 tasks, 6 controls, 77 applications.
ConfigurabilityCAF_Setting__mdt (task path, evidence cap, timeout, logging) and ServiceNow sf.* properties, including a kill switch.
ExtensibilityNew controls appear as grid columns with no code change; LWCs carry record-page and Experience Cloud targets.
RecoverabilitySalesforce org can be rebuilt and repopulated by re-push; single-record Re-sync for drift.

14. Key design decisions

IDDecisionRationale
D1State machine stays in ServiceNowOne scheduler, one truth, one audit trail.
D2Mirror only requests, tasks, controlsConfiguration stays in one place.
D3Upsert by External Id on sys_idReplay-safe; org rebuild survivable.
D4No Salesforce Id stored in ServiceNowOne-directional correlation; orphans on delete are the cheaper problem.
D5Async, fire-and-forget pushA Salesforce outage never rolls back a compliance write.
D6Echo guard plus explicit reconcileThe guard alone strands derived changes, silently.
D7Allow-list rejects the whole callNo invisible partial writes.
D8Detection automatic, repair manual, SN → SF onlyUnattended repair can spread a problem; a disagreeing mirror is stale by definition.
D9Evidence gate in the attest endpointPortal closure behaviour unchanged; pre-existing tasks unaffected.
D10Attestation reuses the existing business ruleOne transition shared by portal and Salesforce.
D11Callout log via platform eventLog survives rollback; no DML between callouts.
D12Client credentials rather than JWTServiceNow JWT provider lacks required claims without custom script; JWT is the production target.
